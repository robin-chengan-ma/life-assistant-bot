# 求職模組 討論紀錄

## 2026-08-08 [標籤：AI] ADR-24：Step 4.1（104 職缺爬蟲）開工前四項設計決策

**狀態**：accepted

**背景**：Step 4.1 開工前，Claude 盤點 FR-33～FR-36 原始規格，發現 FR-35「Gemini 以 Web Search 補充公司背景」與已經拿掉的 Google Search grounding（見 chat-core 討論紀錄 ADR-5）直接衝突，技術上走不通；FR-33（搜尋條件數量）、FR-34a（列表 API 是否已含完整職缺內容）、求職模組使用範圍三點也需要在動工前定案。

**決策**：①FR-35 公司背景改採「Email 協作」機制，不用 Gemini Web Search——每週爬完職缺後找出還沒有背景資料的新公司，寫入資料庫（背景留空）、組 CSV 用 Email 寄給 Robin 自寄自收，Robin 自行上網查完填好後上傳到共用 Google Drive 資料夾，Robinson 偵測到上傳訊息後回填資料庫 ②求職模組僅 Robin 一人可用，`job_search` 開關改為 `owner_only=True` ③FR-33 允許同時存多組搜尋條件（不是覆蓋式） ④FR-34a 深度爬取先採兩階段架構（列表 API 抓清單→詳情頁補齊完整內容），待 Robin 提供實際 API 回應格式後再視情況簡化。

**理由**：決策 1 完全比照專案既有的「知識庫查無答案時，誠實不知道＋請使用者查完提供」模式，把「不知道」換成「查公司背景」，同樣不需要任何外部 Search API、零成本零新技術風險；決策 2 Robin 明確表示求職模組使用範圍先開給自己就好；決策 3 求職條件本質上就可能同時有多個方向；決策 4 sandbox 連不到 104 的網路，保守假設比賭列表 API 已經夠用更穩妥。

**替代方案**：開通 Gemini grounding 計費額度、或串接第三方 Search API（已否決，違反 NFR-1 全免費原則）；一開始就設計成多使用者可用（已否決，先簡化）。

**後果**：`submodules/email` 需要新增支援附件的寄信方法；新增公司資料表（`job_companies`）與搜尋條件表（`job_search_criteria`，支援多組）。

## 2026-08-09 [標籤：AI] ADR-26：Step 4.2（契合度評分與技能缺口分析）開工前設計決策，並修正 FR-36 歸屬

**狀態**：accepted

**背景**：Step 4.2 開工前，Claude 盤點 FR-36～FR-38 發現：①Roadmap 誤把「職缺內容解析」標成 FR-36，FR-36 實際是履歷記錄，應歸屬 Step 4.1 而非 Step 4.2 ②FR-37 契合度評分的比對維度需要先確認哪些要開結構化欄位、哪些要等 Step 4.1 實測才能知道是否可行 ③FR-38 技能缺口分析的顆粒度、排名機制、交付方式都需要定案。

**決策**：①FR-36 歸屬 Step 4.1，新增結構化欄位（年資、期望薪資下限/上限）②FR-38 技能缺口分析以「104 職缺 ID」為單位，不是以公司為單位 ③「應徵人數」「更新時間」兩項評分維度視 Step 4.1 實測結果而定，抓不到直接略過該維度 ④FR-37 契合度評分僅計算「所屬公司背景資料已回填完成」的職缺，背景空白的職缺本次跳過，之後補齊自然被納入 ⑤新增 `is_unliked`（人工標記）／`is_closed`（優先自動判斷，104 API 可取得則自動維護）兩個欄位 ⑥FR-38a「前 30 名」採雙重排名機制（全庫排名／本週新職缺排名）⑦FR-39（應徵成效追蹤）維持 Step 4.3 範圍，本次僅記錄需求。

**理由**：履歷資料是契合度評分的必要輸入，FR-56f 範例已證明履歷收集在體驗上跟搜尋條件設定是同一輪對話；用職缺 ID 當 key 才精準對應到「針對前 30 名職缺整理技能缺口」的字面意思；先測試看看不行再討論，跟 Step 4.1 的保守假設是同一種務實做法。

**替代方案**：改成「事件驅動」——公司背景一填完就立刻觸發評分（已考慮但未採用，會多一套事件觸發機制，複雜度增加）；只做「本週新職缺」單一排名（已否決，Robin 明確要兩種機制併存）。

**後果**：新增職缺本身的資料表（`job_postings`）以及 `years_of_experience`／`expected_salary_min`／`expected_salary_max` 三欄；FR-38b 的 Excel 用 `openpyxl` 產生三張工作表。

## 2026-08-09 [標籤：AI] ADR-27：Step 4.3（應徵成效追蹤）開工前設計決策

**狀態**：accepted

**背景**：Step 4.2 完工後，FR-39／FR-40 原本只記錄 Robin 預告會用的三種狀態語句，細部設計完全空白。需要確認：ID 從哪來、狀態機是否要嚴格照順序推進、FR-40 提到的「並納入評分考量」要不要真的把外部管道職缺送進 Gemini 評分、應徵狀態要用什麼資料結構存。Claude 當下提案「外部管道職缺用獨立新表儲存」，Robin 隨後推翻這個提案，指出職缺資料應該放同一張表、用 `source` 欄位區分來源，理由是「這樣設計才有擴充性」。

**決策**：①推薦 Excel 兩張推薦表新增「104職缺ID」欄位 ②應徵狀態任何時候都能直接設定，不強制順序；新增第四種結束狀態「未錄取／已婉拒」③FR-40 外部管道職缺也要納入 Gemini 契合度評分 ④應徵狀態存成獨立歷程表（非直接覆蓋單一欄位）⑤外部管道職缺與 104 職缺共用同一張 `job_postings`／`job_companies`，新增 `source` 欄位區分來源，外部職缺沒有 104 官方 ID 時由系統配發合成識別碼（例如 `EXT-3`）寫入既有的 `job_id_104` 欄位 ⑥外部職缺與 104 職缺一起參與每週排名機制，不特別區分來源。

**替代方案**：外部管道職缺用獨立新表儲存（Claude 原提案，已被 Robin 否決——理由是獨立表設計擴充性差，之後每加一個新求職平台都要考慮是否要再開一張表）；外部職缺評分但不進排行榜（已考慮但未採用，Robin 明確選擇混在一起排）。

**理由**：真實求職情境中公司不一定照預期順序發通知，嚴格線性狀態機會逼 Robin 補打不存在的中間狀態；獨立歷程表一次到位，不用等以後真的要做統計時回頭補資料結構；用 `source` 欄位統一是更常見、更具擴充性的正規化做法，這個改動還有 Claude 原提案沒想到的附帶好處——既有評分/排名邏輯不區分來源，外部職缺只要符合同樣的資料形狀就會自動被納入既有流程，不需要為外部職缺另外開發一套獨立批次評分機制。

**後果**：`job_postings`／`job_companies` 各自新增 `source` 欄位（`TEXT NOT NULL DEFAULT '104'`），並新增應徵歷程表；`is_closed` 對外部職缺沒有自動判斷依據，預設 `FALSE`。

## 2026-08-18 [標籤：使用者] ADR-28：「求職分析」改名「求職設定」全面選單化，開工前設計決策

**狀態**：accepted

**背景**：求職模組自 Step 4.1～4.3 完工後一直是純文字觸發詞（`/set_job_search`、`ID=XXX 職缺已應徵`等），跟其餘模組已陸續完成的選單化（`collections.py`／`achievements.py`／`youtube_settings:*`）不一致。Robin 提出把主選單「💼 求職分析」改成「💼 求職設定」，子選單列出 10 個項目，其中「我的履歷」「期望工作內容」原本是 FR-36 `save_profile()` 同一輪對話收集的五個欄位之一，「已應徵／獲得面試／拿到 offer」三個狀態各自要獨立清單、「職缺已關閉設定」要新增人工覆寫。

**決策**：①主選單項目 label 改「💼 求職設定」，維持 `key="job_search"` 不變（避免動到既有 `owner_only`／功能開關判斷邏輯）②子選單 10 項，比照 `collections.py`／`achievements.py` 的單層選單＋按鈕操作模式：我的履歷、期望工作內容、必要條件設定（新增項目，見決策 ③）、職缺關鍵字設定、職缺清單（唯讀）、已應徵職缺設定、獲得面試職缺設定、拿到 offer 職缺設定、職缺已關閉設定、其他平台職缺 ③新增「必要條件設定」，把原本併在 `save_profile()` 裡的 `years_of_experience`／`expected_salary_min`／`expected_salary_max` 三個結構化欄位獨立出來，跟「期望工作內容」（純自由文字 `job_expectation`）分開管理 ④履歷／期望工作內容／職缺關鍵字設定三者的「移除」語意為「清空該欄位（或刪除該筆搜尋條件）」，彼此獨立、互不牽動，取代原本 FR-36「整輪對話覆蓋」的設計 ⑤已應徵／獲得面試／拿到 offer 三個選單項目皆為「該狀態的職缺清單，可從清單直接改狀態」，沿用既有 `record_application_status()` append-only 寫入，不新增第 4 種以外的狀態（`offer` 狀態原本就存在，不需要新建）⑥`job_postings` 新增 `is_closed_manual_override` 欄位，允許人工於「職缺已關閉設定」覆寫 104 自動判斷結果；旗標為 `TRUE` 時週爬蟲 `upsert_job_posting()` 的自動 `is_closed` 判斷跳過該筆，人工切回「開啟」時同步清回 `FALSE`。

**理由**：`job_search` key 不變可以避免動到 `menu.py`／`toggles.py` 既有的 owner_only 判斷與功能開關邏輯，只是換皮；必要條件設定獨立成一項，是因為年資／期望薪資是結構化數字欄位，跟履歷／期望工作內容的自由文字欄位在編輯體驗上本來就不同，分開後個別編輯也更清楚；is_closed 若只是單純人工 UPDATE、沒有旗標保護，下一次週爬蟲就會把人工設定蓋掉，等於功能形同虛設。

**替代方案**：把年資／期望薪資留在「期望工作內容」畫面一起編輯（已否決，Robin 明確要求獨立成「必要條件設定」）；`is_closed` 不加保護旗標、直接讓爬蟲每週覆蓋（已否決，人工設定會被下一輪爬蟲蓋掉，違背新增這個功能的目的）。

**後果**：新增 Migration（`job_postings.is_closed_manual_override BOOLEAN NOT NULL DEFAULT FALSE`，先審核後執行）；`router.py` 移除 `_JOB_SEARCH_SETUP_TRIGGERS`／`_ADD_EXTERNAL_JOB_TRIGGERS`／`_MY_APPLICATIONS_TRIGGERS`／`_APPLICATION_STATUS_PATTERN` 文字觸發詞；`job_search.py` 新增選單相關函式；`commands.py` 既有 `start_job_search_setup`／`handle_job_search_*_step` 系列拆解成各子選單各自的狀態機。詳見 SPEC.md 求職模組 FR-41／FR-41a；本次僅完成規格與討論文件定案，實作尚未開始。

### 2026-08-18 補充：清空確認、應徵狀態與職缺開關操作

**狀態**：accepted

**決策**：履歷、期望工作內容的清空，以及單筆職缺關鍵字的刪除，都必須使用按鈕二次確認。已應徵／獲得面試／拿到 Offer 三個清單選取職缺後，可改為「已應徵、已獲得面試、已拿到 Offer、未錄取／已婉拒」四種任一狀態。職缺已關閉設定顯示全部職缺（包括目前已關閉者），並提供「標記關閉／重新開啟」切換。

**理由**：清空及刪除均可能失去使用者輸入資料，需避免誤觸；應徵流程不保證線性，維持 ADR-27 的任意狀態設定；顯示全部職缺才能讓使用者撤銷先前的人工關閉判斷。

### 2026-08-18 補充：Mobile 推薦與歷史分布的關閉職缺規則

**狀態**：accepted

**背景**：人工關閉功能上線後，Mobile 求職分析仍把關閉職缺同時放進 Top 推薦與契合度分布，需區分「目前值得採取行動的推薦」與「本期曾分析過的歷史樣本」。

**決策**：Mobile「本期 Top 推薦」排除 `is_closed=TRUE` 的職缺；契合度分布仍統計本期全部已分析職缺，包含後續自動或人工關閉者。

**理由**：Top 推薦不應顯示已無法應徵的工作；契合度分布用於觀察該期間分析結果，保留關閉職缺才能避免歷史統計因狀態變更而失真。

**後果**：後端同一份求職分析資料需同時保留全部職缺供分布計算，並只從未關閉子集合產生推薦清單；不修改資料表，也不擴張 DRAFT 中尚未定案的求職圖表改版。
