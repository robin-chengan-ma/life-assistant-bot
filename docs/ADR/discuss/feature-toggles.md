# 功能開關系統 討論紀錄

## 2026-07-30 [標籤：AI] ADR-1：既有對話狀態 dict 新增 `flow` 欄位做流程區分

**狀態**：accepted

**背景**：Step 1.1 的 `ConversationStateStore` 狀態 dict 原本只有 `{"step": ...}`，因為當時只有一種對話流（Owner 設定通關密碼）。Step 1.2 新增兩種對話流（`/my_toggles`、`/set_toggle`），且 `/my_toggles` 一般使用者也能觸發，路由層需要先判斷「目前這個進行中的對話屬於哪一種流程」才能分派到正確的處理函式。

**討論內容**：比較方案 A（狀態 dict 新增 `flow` 欄位，單一 store 支援多種流程，但需要對既有 `set_invite_codes` 流程的狀態 dict 做破壞性變更）與方案 B（每種流程各自一個獨立的 `ConversationStateStore` 實例，不需改既有結構，但 `router.py` 需同時查詢多個 store，且無法防止同一使用者同時卡在兩個流程）。

**決策**：採方案 A。

**理由**：方案 B 的「多 store 查詢」在使用者同時操作兩種流程時會產生狀態不一致的風險，方案 A 用單一 `flow` 欄位明確排他，邏輯更單純；既有測試的破壞性變更範圍很小，且本專案測試覆蓋率 100%，重構風險可控。

**後果**：`commands.start_set_invite_codes`／`handle_set_invite_codes_step` 的狀態 dict 從 `{"step": ...}` 改為 `{"flow": "set_invite_codes", "step": ...}`，`tests/bot/test_commands.py`、`tests/bot/test_router.py` 對應斷言需同步更新。

## 2026-08-15 [標籤：使用者] 特殊功能改為 Robin 專屬

**狀態**：accepted（supersedes 既有「一般使用者自管、Owner 代管」及「Owner 可替家人開啟特殊功能」決策）

**背景**：Telegram 重構盤點確認「技術分享」、「求職分析」與「考試成績」只供 Robin 使用，非管理者沒有使用情境；其他一般功能則全面開放，不需要功能開關。

**決策**：三項特殊功能以 `is_owner` 限定 Robin；非管理者不顯示 Telegram／Mobile 入口，後端拒絕偽造 Callback、舊指令與 API 存取。權限管理不提供家人特殊功能授權。若保留三項開關，只能控制 Robin 自己的爬蟲、內容產生與推播，不建立家人開關或個別排程。

**理由**：移除不會使用的授權維度，可降低資料、權限、選單與測試複雜度，並避免一般使用者誤觸 Robin 專屬資料。

**後果**：重構時停用 `/my_toggles`、`/set_toggle` 與一般使用者功能開關流程；既有 `feature_toggles` 表與資料保留，不做破壞性刪除。Reference 在程式完成前仍記錄現行實作，完成後再同步成新狀態。

## 2026-08-18 [標籤：使用者] 主選單「排程設定」改名「功能開關與排程設定」，排入下個階段

**狀態**：superseded（由下方同日「功能開關、通知接收與系統工作分層」取代）

**背景**：求職設定選單化開工前盤點（見 `docs/ADR/discuss/job-search.md` 2026-08-18 ADR-28）順帶提及：FR-1／FR-2 定案「若保留 `tech_intel`／`job_search`／`certificate` 三項開關，只控制 Robin 自己的爬蟲、內容產生與推播」，但目前主選單「⏰ 排程設定」（FR-6f）只列待辦、重要日子、目標日期等一般推播設定，這三項特殊功能開關始終沒有 Telegram 選單入口可以開/關。

**決策**：主選單「⏰ 排程設定」改名「⏰ 功能開關與排程設定」，比照既有排程設定的「是否啟用」按鈕模式，新增這三項開關的選單化開啟/關閉操作。本次（求職設定選單化）不動這個項目，實作排入下一階段。

**理由**：三項開關的產品需求（FR-1／FR-2）本來就已定案，只是選單入口一直沒補上；跟求職設定選單化放在同一批次會讓單次改動範圍過大，先分開排程。

**替代方案**：維持「排程設定」名稱、開關另外開一個獨立主選單項目（已否決，Robin 傾向合併進同一個項目，避免主選單項目數量繼續增加）。

**後果**：`menu.py` 的 `MAIN_MENU_ITEMS`／`schedule` 項目 label 待下一階段改動；`_NOT_YET_IMPLEMENTED_KEYS` 目前仍包含 `schedule`，這次不移除。

## 2026-08-18 [標籤：使用者] 功能開關、通知接收與系統工作分層

**狀態**：accepted

**背景**：實作前盤點確認現行 `/healthz` 同時承載使用者通知、Owner 專屬內容工作與內部維護工作；若只提供單一開關，會混淆「停止功能」與「只是不通知」。另發現每日未記帳與未完成考題提醒不符合已定案的低干擾通知邊界，目標與旅遊日期雖已同步 `important_days`，卻缺少通用 Telegram 發送器。

**決策**：①一般使用者只看自己的通知排程；Owner 額外看三項功能開關與全部系統工作。②「技術分享」開關同時控制每日技術摘要與 Youtube 推薦；求職與考試使用目前正式名稱。③關閉功能會停止收集、爬蟲、內容生成與推播；關閉通知只停止送達，背景工作照常執行。④系統工作只供 Owner 唯讀查看，不開放任意頻率修改。⑤移除未記帳與未完成考題催促。⑥所有具日期的目標及旅遊行程統一由 `important_days` 規則、通知對象與去重機制發送。

**理由**：把功能生命週期、通知偏好與系統維運工作分開，可避免使用者為了不收訊息而意外停止資料處理，也能讓所有目標與旅遊提醒共用單一規則來源。

**後果**：新增 migration `0093` 的 `notification_preferences`；主選單改名並接上 `schedule:*` Callback；新增統一日期提醒發送器，移除兩項日常催促與舊固定 7 天目標期限提醒。查無通知設定時預設接收，確保既有使用者升級後行為相容。
