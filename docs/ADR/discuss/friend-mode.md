# 好友模式 討論紀錄

## 2026-08-08 [標籤：AI] ADR-22：Step 3.5（好友模式）規格定案——心情趨勢改文字摘要、範圍限被動模式、資料來源動態涵蓋所有已使用模組

**狀態**：accepted

**背景**：FR-51／FR-52 原始規格過於簡略（僅一行文字），開工前 Robin 要求先聽 Claude 對這個功能的設計想法再定案，經討論並用 AskUserQuestion 確認三個關鍵決策：①FR-51「心情趨勢圖」跟「圖表統一交給 Phase 4 Mobile App」的既有架構決策是否衝突、如何處理 ②這次要做到「僅被動模式」還是連「主動關懷推播」也一起做 ③好友聊天時要讀哪些模組的近期紀錄當素材——固定清單或動態涵蓋該使用者所有實際使用中的模組。

**決策**：①FR-51 改為文字／emoji 摘要，不做圖片圖表，比照 FR-44（記帳）／FR-29（證照成效）既有慣例 ②Step 3.5 這次只做被動模式（使用者主動觸發「陪我聊聊」才生成陪伴對話），不做排程主動關懷推播 ③資料來源動態涵蓋該使用者所有已開啟且近期（預設近 7 天）有資料的模組，不寫死固定清單——因此 Robin 觸發時可能包含技術情報／證照準備等僅 Robin 可用模組的近況，其他家人觸發時則只會看到自己有用到的模組。

**理由**：延續專案一貫的「圖表統一在 App 呈現、Telegram 端只做文字摘要」架構原則；先驗證「被動陪伴聊天」這個核心價值，範圍小、風險低，主動關懷需要額外定義「異常訊號判斷規則」與「推播頻率」，複雜度更高；「所有用到的功能模組」意味著好友模式的價值取決於使用者實際使用了哪些功能，寫死清單會讓 Robin 聊天時漏掉他實際在乎的內容。

**替代方案**：現在就用繪圖套件或 LLM 生成圖片圖表（已否決，會產生跟未來 App 化圖表不一致的兩套邏輯）；被動＋主動一起做（已否決，主動關懷的判斷規則需要更多討論）；固定清單排除 Robin 專屬模組（已否決，會漏掉 Robin 實際在意的技術情報/證照進度）。

**後果**：好友聊天的 Prompt 組裝邏輯需要逐一呼叫各模組既有的「近期資料查詢」函式，複用既有函式而非重新開發資料存取層；「近期」的時間窗口先訂為 7 天，純粹是程式常數；觸發詞「陪我聊聊」只做單輪生成完整回覆，不需要新增 `pending_*` 對話狀態機。
