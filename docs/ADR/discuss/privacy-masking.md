# 個資偵測與遮蔽機制 討論紀錄

## 2026-07-29 [標籤：AI] 語音與個資的安全護欄（原記錄於 robinson SPEC.md ADR-5，個資部分）

**狀態**：accepted

**背景**：個資外洩風險需要主動防護而非事後補救（語音時長部分的討論已移至 `docs/ADR/discuss/voice-safety.md`）。

**討論內容**：比較「事後人工審查」（不即時、無法防止額度已被消耗）與「完全禁止語音修正」（使用者體驗差）等方案；最終聚焦在「偵測到個資關鍵字時主動提示收回並清除相關記錄」這個方向。

**決策**：偵測到個資關鍵字（身分證字號、電話、信用卡卡號格式）時主動提示收回並清除相關記錄。

**理由**：對應 Robin 明確列出的「Robinson 警察證」規則，屬於安全與成本雙重考量的硬性限制。

**後果**：需要在對話流程中加入個資偵測（regex / Gemini 分類）邏輯，後續於 Step 1.5 展開為 Regex + LLM 雙層防線（見下方 2026-08-02 條目）。

## 2026-08-02 [標籤：AI] ADR-1：LLM 語意層改用獨立 Key，不共用聊天 Key

**狀態**：accepted

**背景**：FR-13b 要求「Regex 硬規則＋LLM 語意辨識」雙層防線，代表語意層很可能要對每一則使用者訊息都多跑一次額外的 Gemini 呼叫。本專案先前已多次撞到 429，Robin 對額度消耗非常敏感。

**討論內容**：比較方案 A（新申請一把專用 Key `GEMINI_API_PRIVACY_KEY`，額度隔離但需額外申請）、方案 B（沿用既有聊天 Key，實作簡單但讓吃緊的配額更快用完）、方案 C（先只做 Regex 層，語意層留待後續，不影響額度但不符合完整要求）。

**決策**：採方案 A（Robin 2026-08-02 明確選擇「新申請一把專用 Key」）。

**理由**：與既有的多 Key 分流慣例一致，額度隔離、互不影響。

**後果**：`.env.example` 新增 `GEMINI_API_PRIVACY_KEY`；`webhook.py` 需額外初始化一個 `LLMClient`。

## 2026-08-02 [標籤：AI] ADR-2：語意層 Key 缺失時的降級行為

**狀態**：accepted

**背景**：ADR-1 決定語意層改用獨立 Key，但這把 Key 需要 Robin 額外申請，可能有一段時間尚未就緒。

**決策**：`mask_text()` 的 `llm_client` 參數允許傳 `None`；為 `None` 時只執行 Regex 層，不拋出例外、不中斷訊息處理流程。

**理由**：個資遮蔽是輔助防線，不應該因為選配的第二層 Key 還沒設定好就讓整個訊息處理失敗；Regex 層本身不依賴任何外部服務，永遠可以運作。

## 2026-08-04 [標籤：AI] ADR-3：語意層呼叫遇到暫時性外部錯誤時的降級行為

**狀態**：accepted

**背景**：Robin 實際使用時，`mask_with_llm()` 呼叫 Gemini 撞到 `503 UNAVAILABLE`，但 `mask_text()` 當時沒有捕捉這個例外，導致整則訊息處理完全中斷、使用者完全沒收到任何回覆。

**討論內容**：比較方案 A（`except Exception` 全面捕捉＋降級成 Regex-only，實作最簡單但連真正的程式錯誤也會被吞掉）、方案 B（只捕捉已知的暫時性錯誤類型，更精確但與第三方套件例外型別耦合度高）、方案 C（等 FR-19i 完整重試機制一起做，範圍大且這段期間持續會撞到問題）。

**決策**：採方案 A。

**理由**：跟 ADR-2 同一個理由——語意層是輔助防線，不應該讓這層選配的輔助防線因為外部服務暫時性故障就讓整個訊息處理失敗；此問題會直接讓使用者完全收不到回覆，風險層級高於「重試後才成功」的體驗優化。

**後果**：`mask_text()` 呼叫 `mask_with_llm()` 新增 `try/except Exception`，任何呼叫失敗都優雅降級成只回傳 Regex 層結果並記錄 warning log。
