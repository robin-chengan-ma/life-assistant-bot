# 羅賓森 Mobile App 討論紀錄

> 本檔案彙整原 `docs/specs/mobile-app/SPEC.md` 的 ADR-1，以及原記錄於 robinson 母 spec、與 Mobile App 架構/技術棧/登入機制選型相關的 ADR-14、ADR-28（因討論的是同一個功能，遷移時合併於此）。

## 2026-08-04 [標籤：AI] 視覺化後台改採 Mobile App（React Native + Expo），取代 Notion（原記錄於 robinson SPEC.md ADR-14，supersede ADR-1 的後台選型部分）

**狀態**：superseded（2026-08-09 由「唯讀分析＋可編輯設定管理」決策取代相關定位）

**背景**：原本選定 Notion 作為視覺化後台（上手快、適合非工程背景的家人瀏覽）。Robin 重新評估後，希望改用自建的 Mobile App，取得更客製化的 BI Dashboard 體驗與獨立的多用戶登入機制。

**決策**：①移除所有 Notion API 串接與資料同步邏輯 ②架構確立為「Telegram Bot（LUI）+ Mobile App（Rich GUI）」兩前台分工：Telegram 負責所有輸入與 CRUD 控制，Mobile App 專注 BI 圖表展示、唯讀，不提供任何寫入/CRUD 操作入口 ③技術棧確定採用 React Native + Expo ④新增多用戶登入機制（`user_name`／稱謂／`APP Access Token`）。

**替代方案**：維持 Notion（已否決，客製化程度低、多用戶登入機制需另外拼湊）；改建 Web Dashboard（已否決，家人主要透過手機使用，Native App 體驗更佳）。

**理由**：Notion 客製化互動式篩選能力弱、且沒有原生多用戶權限控管機制；React Native + Expo 是目前最成熟的跨平台方案之一，免費方案足敷家庭規模使用。

**後果**：Phase 5（Notion 後台）取消，併入 Phase 4；`users` 資料表未來需新增 `app_access_token` 欄位（後由 ADR-28 取代為 `password_hash`）。

## 2026-08-09 [標籤：AI] ADR-1：「客訴回饋」頁拆成「使用者客訴」與「系統錯誤回報」兩區塊，「解法」欄位只加在系統錯誤回報

**狀態**：superseded（錯誤管理入口於 2026-08-18 改由 Telegram Owner 選單統一處理；客訴功能另已取消）

**背景**：本文件初版誤將「解法」欄位設計加在 `complaints`（使用者客訴）上。Robin 後續澄清：使用者主動送出的客訴內容他只是查看，不需要解法欄位；真正需要追蹤處理進度的是系統主動推送給他的錯誤回報。Robin 同時要求解法的記錄不能只能在 App 操作，Telegram 也要能下指令記錄。

**決策**：①「客訴回饋」頁拆成「使用者客訴」（`complaints`，純唯讀）與「系統錯誤回報」（`system_error_reports`，含 `resolution` 欄位）兩個區塊 ②`resolution` 欄位同時支援 App 與 Telegram 兩種入口寫入，兩個入口呼叫同一支 service 層函式 ③`_notify_robin_of_error()` 私訊 Robin 時附上「錯誤ID=N」。

**替代方案**：`complaints` 表直接加 `resolution` 欄位（已否決，Robin 明確表示使用者客訴不需要這個欄位，混用會讓兩種性質不同的資料共用一張表）。

**理由**：使用者客訴與系統錯誤回報服務的目的完全不同；Robin 平常主要透過 Telegram 互動，收到錯誤通知當下直接回一行記錄解法比切到 App 更符合實際使用情境。

**後果**：robinson SPEC.md 新增 FR-19j；「客訴回饋頁」歸屬唯讀分析頁面的子 Step 開發，不另拆獨立 Step。

**取代決策**：見 `docs/ADR/discuss/service-resilience.md` 2026-08-18「Mobile App 納入異常、康復與錯誤管理」。

## 2026-08-09 [標籤：AI] Mobile App 範疇由「唯讀 BI Dashboard」擴大為「唯讀分析＋可編輯設定管理」，並改採帳密登入（原記錄於 robinson SPEC.md ADR-28，supersede ADR-14 相關部分）

**狀態**：accepted（FR-69／FR-70／FR-71 設定頁部分於 2026-08-14 被正式取消，其餘決策維持有效）

**背景**：Phase 4 主線（求職模組）全數完成後，Robin 要求盤點現有所有功能模組再決定 App 要放哪些功能，並提出「APP 也可以設定目標和指標，以及各功能開關，不是只有 Telegram 可以設定而已」——這與原本「App 端原則上不提供新增/修改/刪除資料的操作入口」的唯讀定位直接牴觸。Robin 同時提出登入頁互動細節（使用者ID＋密碼、忘記密碼、保持登入），其中「忘記密碼→立刻寄出密碼到 Telegram」與「個人基本資訊頁面顯示密碼」隱含系統需要能取得使用者的密碼明碼，這與密碼安全最佳實踐（單向雜湊、不可逆）有衝突，屬於 Claude 需要主動指出並提出替代方案的技術判斷。

**決策**：①App 定位改為「唯讀分析頁面＋可編輯設定頁面」雙軌設計，新增目標與指標設定、功能開關、排程設定（僅 Robin）、APP設定四類可編輯頁面；高頻「記一筆」操作仍以 Telegram 為主 ②登入機制由 `APP Access Token` 改為帳密登入 ③密碼儲存採單向雜湊（bcrypt/argon2），「忘記密碼」改為「系統產生新隨機密碼覆蓋舊密碼並透過 Telegram 發送」（重設，非復原） ④保持登入採 Refresh Token 機制，效期 30 天，存於裝置本機 Expo SecureStore ⑤排程設定範疇限縮為 Robin 專屬的 6 項既有排程功能 ⑥目標與指標設定頁面補上盤點發現的 3 處遺漏（求職履歷/期望工作、證照每日出題設定、技術情報主題訂閱）。

**替代方案**：密碼採可逆加密儲存（已否決，一旦金鑰或資料庫外洩，所有密碼會同時明碼曝光，風險遠高於「忘記密碼」情境本身的體驗損失）；排程設定開放給所有使用者所有排程（已否決，需額外設計「每個使用者各自獨立排程」的資料模型，複雜度與實際需求不成比例）。

**理由**：App 端目前已經是使用者最常拿在手上的介面，結構化表單類設定用 App 操作體感更好，但高頻的「記一筆」操作留在 Telegram 因為一句話就能講完；忘記密碼流程要求系統能把可用密碼交給使用者，若採單向雜湊系統本身也無法還原明碼，只能重設為新密碼——這是資安最佳實踐與原始需求之間風險最低的折衷。

**後果**：`users` 表新增欄位規劃（`password_hash`、`refresh_token_hash`、`refresh_token_expires_at`）取代原本規劃的 `app_access_token`；Phase 4 開工時的實作規模比原規劃大，建議依風險與相依順序拆成更細的子 Step 逐一推進（登入與 Token 機制→唯讀分析頁面→個人基本資訊＋目標設定→功能開關＋APP設定→排程設定）。

## 2026-08-11 [標籤：AI] FR-64a 藍牙體重計方案終止：Web Bluetooth／Bluefy POC 失敗，全面移除 BLE 改為手動輸入體重

**狀態**：accepted（supersede robinson SPEC.md 2026-08-08 新增的 FR-64a 藍牙體重計規格）

**背景**：FR-64a 原規劃由 App 直接連藍牙體重計（廣播名稱 `Yoda1`）自動寫入體重。原生 BLE 版本已實作完成（`react-native-ble-plx` 掃描、Yoda1 穩定封包 `13 88 00 00 25 00` 解析、Big Endian 除以 100 換算公斤、`POST /api/app/body/weight-logs` 寫入），但原生 BLE 模組不支援 Web、Expo Go 與模擬器，必須做 Development Build 才能實機使用。Robin 因此提出零成本替代方案：改用 PWA＋Bluefy（iOS 上支援 Web Bluetooth 的第三方瀏覽器），這樣就不必走 Development Build 或 App Store／Google Play 發布。

**討論內容**：建立隔離的 `/ble-test` 診斷頁做相容性 POC，不動正式登入、首頁量測與體重寫入流程，並用免帳號 Cloudflare Quick Tunnel 提供臨時 HTTPS 網址給 iPhone 實測。三次 iPhone／Bluefy 3.9.3 實機測試結果：①第一次確認 HTTPS、`navigator.bluetooth`、Yoda1 裝置選擇與 `watchAdvertisements()` 全部可用 ②第二次 `requestDevice()` 能選到 Yoda1、`watchAdvertisements()` method 存在，但 15 秒內完全沒有觸發 `advertisementreceived`，也沒有 Manufacturer Data 空值或解析失敗紀錄——問題出在瀏覽器沒把廣播事件交給 Web App，而不是 Yoda1 parser ③追加 `navigator.bluetooth.requestLEScan()` 做最後相容性檢查，最終確認 Bluefy 不提供該 API，回退的 `watchAdvertisements()` 仍收不到任何事件。

**決策**：①PWA＋Bluefy 方案否決，不採用 ②同時決定連原生 BLE 一起全面移除：Android、iOS 與 Web 全平台不再掃描 Yoda1、不要求藍牙權限、不保留 Development Build 專用套件 ③體重改為手動輸入——首頁體重卡片按鈕由「開始量測」改為「記錄一下」，開啟 App 內 Modal 輸入，範圍固定 `40.0～150.0 kg`（含邊界）、統一四捨五入至小數點後第一位、第二層「XX.X 公斤是否正確？」確認後才呼叫 API ④API 邊界同步強制 `40～150 kg` 驗證與後端四捨五入，即使繞過前端直接呼叫也不能落地超範圍數值。

**替代方案**：走 Expo Development Build ＋原生 BLE（已否決，等同要求 Robin 與家人安裝非商店版本 App，維運與發布成本高於「手動輸入一個數字」省下的力氣）；維持 PWA＋Bluefy（已由三次實機 POC 否決，`Connectable: No` 的被動廣播體重計無法把資料交給 Web App）。

**理由**：Yoda1 是不可連線（`Connectable: No`）的被動廣播裝置，Web Bluetooth 在 Bluefy 上拿不到它的 Manufacturer Data，這是瀏覽器能力限制而非實作缺陷，沒有繞路空間；而保留原生 BLE 就得綁 Development Build，對一個家用小工具而言投報率不成比例。

**後果**：刪除 `mobile/src/services/weightScale*.ts`、`mobile/src/services/weightScaleProtocol.ts` 與 `mobile/app/ble-test.tsx`；`mobile/app.config.ts` 移除 BLE config plugin、iOS 藍牙用途文字與背景藍牙設定；`mobile/package.json`／`pnpm-lock.yaml` 移除 `react-native-ble-plx@3.5.1`、`expo-dev-client@57.0.11` 及 8 個相關安裝項目，並刪除只為此建立的 `mobile/pnpm-workspace.yaml`。實機驗證完成後已關閉 Cloudflare Quick Tunnel，臨時網址失效。SPEC.md 的 FR-64a 已同步改為「藍牙體重計整合已全面移除，改為手動輸入按鈕『記錄一下』」。

## 2026-08-12 [標籤：AI] FR-69／FR-70／FR-71（目標與指標設定／功能開關／排程設定頁）本輪整批跳過

**狀態**：superseded（2026-08-14 由「正式取消 FR-69／FR-70／FR-71」決策取代）

**背景**：Step 4.4／4.5 主線開發（FR-64／FR-64a／FR-65／FR-67／FR-68／FR-72）由 Codex Desktop 完成並準備收尾，`docs/ADR/discuss/mobile-app.md` 2026-08-09 條目原規劃的四類可編輯設定頁面中，「目標與指標設定」（FR-69）、「功能開關」（FR-70）、「排程設定，僅 Robin」（FR-71）三頁尚未開工。Robin 明確指示本輪先不做，只完成 APP 設定（FR-72）與其餘既定範圍。

**決策**：FR-69、FR-70、FR-71 本輪全部跳過，不建立頁面、API 或資料表；右上角個人選單「APP 設定」直接接在「個人基本資訊」之後、登出之前，不預留這三項的入口。既有 Telegram 對話流程（`/set_body_goal`／`/my_toggles`／`/set_toggle` 等）維持原樣，不受影響，使用者仍可透過 Telegram 完成對應設定。

**替代方案**：本輪一併做完（已否決，Robin 評估這三頁的實作規模與目前優先順序不成比例，決定先讓已完成的部分正式上線，其餘留待未來有實際需求再排入）。

**理由**：「記一筆」等高頻操作已透過 Telegram 覆蓋；FR-69～FR-71 屬於低頻率的結構化設定操作，透過 Telegram 既有指令仍可達成同樣效果，App 端補齊的急迫性較低，優先讓已完成的登入/分析/個人資訊/APP設定盡快正式上線更符合效益。

**後果**：`docs/specs/SPEC.md`「羅賓森 Mobile App」區塊 FR-69～FR-71 標註為「依 Robin 指示跳過，不排入目前 Roadmap」；`docs/specs/PROGRESS.md` 時程與任務狀態表新增一列追蹤（狀態：待辦）。未來若要重新排入 Roadmap，需先確認實際需求並回到本檔案新增後續決策紀錄，不直接覆寫本條。

## 2026-08-14 [標籤：使用者] FR-69／FR-70／FR-71 由暫時跳過改為正式取消

**狀態**：accepted（supersede 2026-08-12「本輪整批跳過」決策）

**背景**：文件治理盤點發現，FR-69／FR-70／FR-71 雖已於 2026-08-12 決定不開工，仍被 PROGRESS 列為正式待辦，與 Robin 先前「這三個不做、直接跳過」及目前文件生命週期規則不一致。

**討論內容**：Robin 確認這三項不應繼續留在 Roadmap，而應移至 DRAFT 的「已取消」。取消範圍僅限 Mobile App 的三個設定頁，不影響 Telegram 既有目標、功能開關與排程能力。

**決策**：正式取消 FR-69「目標與指標設定」、FR-70「功能開關頁」與 FR-71「Robin 專屬排程設定」。從 SPEC 移除現行 FR 條目、從 PROGRESS 移除待辦，並在 DRAFT「已取消」保留索引。

**理由**：三項設定已有 Telegram 既有流程可使用，App 端沒有足以支持額外頁面、API 與維護成本的實際需求；持續列為 Roadmap 待辦會造成錯誤期待。

**後果**：Mobile App 不提供這三個入口，也不預留相關頁面、API 或資料表。若未來重新提出相同需求，必須視為新需求重新進入 DRAFT、討論與定案流程，不得直接恢復舊 FR。

## 2026-08-14 [標籤：使用者] Mobile App 飲食／運動輸入模式、資料來源圖例與心情 Emoji 調整

**狀態**：accepted

**背景**：既有 Mobile App 飲食與運動紀錄主要依賴 AI 估算，無法清楚區分使用者人工輸入與 AI 估算資料；窄螢幕上的紀錄視窗按鈕亦有跑版問題，心情分類則缺少一致的視覺提示。

**討論內容**：①運動新增「時間／熱量」頁籤；熱量模式由使用者直接輸入正數並四捨五入為整數，不呼叫 AI。重訓搭配時間模式時新增「強度與組數」，供 AI 估算參考。②飲水量獨立且選填，只接受整數毫升；飲食提供「文字／照片」頁籤。文字內容必填，可選 AI 計算或人工輸入；人工模式的脂肪、碳水化合物、蛋白質與熱量全部必填，三大營養素以公克記錄至小數點後一位，熱量四捨五入為整數，不強制驗證營養素換算熱量是否一致。③照片流程固定為「拍照／相簿 → AI 辨識名稱與份量 → 使用者編輯確認 → 選擇 AI／人工計算 → 二次確認 → 儲存」；辨識失敗時保留照片並允許重試或切換文字。④只要使用者修改任一 AI 估算營養或熱量數值，整筆來源改列人工；完全採用 AI 結果才列 AI。⑤同日混合資料在圖表拆成人工實心圓與 AI 空心圓兩組資料，Tooltip 顯示人工、AI 與合計。⑥六種心情 Emoji 統一套用 Mobile App 各顯示位置，不調整 Telegram。⑦紀錄視窗的取消、清除、確認按鈕維持同列等寬彈性布局，不得在窄螢幕換行。

**決策**：上述流程與顯示規則全部確認。運動熱量限制 `1～5,000` 大卡；飲食熱量限制 `1～10,000` 大卡；脂肪、碳水化合物與蛋白質各限制 `0～1,000.0` 公克，欄位必填但允許 `0`；飲水量選填，有填時限制 `1～10,000` 毫升。照片辨識失敗時只保留在當次紀錄視窗，允許原圖重試或切換文字；關閉視窗、離開頁面或重新整理後清除，不做跨頁持久化。前後端必須採相同數值邊界，超出範圍時禁止儲存。

**理由**：人工與 AI 雙軌輸入讓使用者可以自行採用可信數據，也能保留 AI 的便利性；明確記錄資料來源才能讓圖表正確揭露估算性質。欄位邊界與照片保留週期會影響前後端驗證、資料庫欄位與暫存機制，不能由實作者自行假設。

**後果**：需求已從 DRAFT 移除並升級至 SPEC 的 FR-64。實作需要擴充飲食／運動資料來源欄位、運動輸入模式與重訓內容、人工營養欄位驗證、照片流程狀態、分析 API 分組與圖表圖例；Telegram 顯示與流程不在本次異動範圍。

## 2026-08-12 [標籤：AI] 收藏清單／旅遊行程／探索地圖／成果展示新功能方向與地圖技術選型

**狀態**：accepted（2026-08-14 完成需求確認並升級至 `docs/specs/SPEC.md` FR-73～FR-76a）

**背景**：Mobile App 主線（FR-64／FR-64a／FR-65／FR-67／FR-68／FR-72）落地後，Robin 提出一組規格範圍外的新方向：把「想去但還沒去」的餐廳、景點、山岳、住宿、活動先存成收藏清單，規劃時併進旅遊行程，實際去過之後變成探索地圖上的紀錄，符合條件再形成成果卡片。這組功能需要地圖能力，而目前實際交付方式是 Expo Web 網址（iPhone 與 Android 都用瀏覽器開），因此得先確認跨平台地圖方案可行才談功能規格。

**討論內容**：先做隔離的 `mobile/app/map-poc.tsx` 技術驗證頁（三筆假資料、不讀寫正式資料），比較 Leaflet＋OpenStreetMap 與 Expo Maps。之後接著完成收藏清單第一階段實作（`0071`～`0077` migration、`app_collections` Service／API、首頁收藏卡片與唯讀收藏頁），並在過程中把整組功能的產品邏輯談定。

**決策**：①地圖採 Leaflet 1.9.4＋OpenStreetMap 圖磚，不採 Expo Maps ②四項功能的生活流程定為「收藏清單 → 旅遊行程 → 探索紀錄 → 成果卡片」 ③首頁是三者的資料維護入口（新增／編輯／刪除），左側選單進入的頁面只負責顯示、篩選與分析 ④這三項不受「Mobile App 僅提供今日紀錄」限制，可異動不同日期的紀錄 ⑤旅行支出仍以既有 `transactions` 為唯一金額來源，用 `trip_id` 關聯行程，旅遊行程不另存一份相同支出 ⑥刪除行程時，收藏、探索事件與記帳只把 `trip_id` 設為 `NULL`，只有行程內專屬日程項目隨行程刪除 ⑦地址搜尋若後續由後端代理 OpenStreetMap Nominatim，必須遵守公開服務限制：由使用者明確按下搜尋才呼叫、不得做即時自動完成、全應用每秒最多一次請求、提供識別資訊與署名、快取結果，並保留日後替換搜尋服務的能力。

## 2026-08-14 [標籤：使用者] 收藏地址選填與漸進式近似定位

**狀態**：accepted

**背景**：部分收藏只確定國家與區域／城市，或 Nominatim 有道路資料但缺少精確門牌；若強制地址必填或精確門牌找不到就完全拒絕定位，會妨礙收藏建立與探索地圖使用。

**討論內容**：使用者確認地址應明確標示為選填；即使輸入詳細地址但找不到精確門牌，也可逐步放大搜尋範圍，接受道路或城市層級近似位置。探索地圖主要依國家與區域／城市篩選，因此可接受一定程度的座標誤差。

**決策**：①所有收藏的地址改為選填 ②無地址仍可儲存，並可由使用者明確按下「定位區域」以國家及區域／城市取得近似座標；只有尚未執行定位時顯示「尚未執行定位」 ③有地址時依精確地址、道路、區域／城市逐級搜尋 ④近似結果必須標示定位精度與實際採用的顯示名稱，不得偽裝成精確門牌 ⑤探索地圖仍依國家與區域／城市篩選，無任何可用定位結果時才列入無法定位清單。本決策取代本檔較早期「地點類收藏地址必填」條款。

**理由**：收藏是候選清單，不應因暫時沒有地址而無法建立；探索地圖的主要用途是區域回顧，不要求導航等級精度。

**後果**：需調整 FR-73／FR-75、收藏前後端驗證、Geocoding fallback／快取結果與 Mobile 提示；既有資料欄位可沿用，不需新增收藏地址欄位。

**替代方案**：Expo Maps（已否決，官方套件只支援 Android／iOS 原生、目前仍為 alpha、不支援 Expo Go，且 Android 需要 Google Maps SDK 設定，與「用瀏覽器開 Expo Web 網址」的實際交付方式不合）。

**理由**：Leaflet 是純前端方案，在 Expo Web 直接可用、免金鑰、免原生建置，Web bundle 也可延遲載入（實測延遲載入 bundle 約 149 KB、CSS 約 11 KB），對目前的交付方式最省事；OpenStreetMap 圖磚免費但屬公共服務，所以搜尋代理的使用限制必須一開始就寫進決策，避免日後被封鎖。

**後果**：`mobile/package.json` 新增正式依賴 `leaflet@1.9.4` 與型別依賴 `@types/leaflet@1.9.22`；正式功能的地圖必須顯示 OpenStreetMap 著作權署名。目前只有收藏清單第一階段與 API 串接，旅遊行程、正式探索流程及成果新增仍待依 FR-73～FR-76a 完成；`0071`～`0077` migration 已建立，實作時需先核對既有 Schema 是否符合定案內容。

## 2026-08-14 [標籤：使用者] 收藏、旅遊行程、探索地圖與成果展示的功能邊界重新釐清

**狀態**：accepted

**背景**：既有 POC 與第一階段實作包含部分尚未確認必要性的欄位與入口，需要先依實際產品用途重新收斂，再決定正式資料模型與後續開發內容。

**討論內容**：①收藏清單定位為「想去的地點／想執行的活動」候選池，之後可被組合成旅遊行程；使用者傾向移除優先程度、想去日期與縣市欄位，只保留國家及區域／城市等必要位置資訊。②旅遊行程是由多筆收藏組成的當天或幾天幾夜行程，不做精細到每日時間點的旅遊推薦或排程系統。③探索地圖只呈現已造訪的歷史事件，可依國家或區域／城市篩選；點擊地圖標記顯示當時的收藏字卡，不提供獨立「新增探索」，探索資料一律由收藏生命週期產生。④成果展示用卡片呈現已完成目標或解鎖成就；目前尚未實作新增成果。

**決策**：收藏狀態流轉、旅遊行程日期與排序粒度、探索歷史快照與重複造訪、成果建立來源均已由下列補充條目完成確認，正式定案為 SPEC FR-73～FR-76a。

**理由**：四項功能不是四套彼此獨立的 CRUD；前三者應形成「收藏候選 → 組成行程 → 完成造訪 → 地圖回顧」的生命週期，成果展示則是跨模組的成就牆。若未先確認狀態與來源，既有收藏資料日後編輯可能錯誤改寫探索歷史。

**後果**：需求已自 DRAFT 移除並升級至 SPEC，排入 Phase 5；程式碼仍須依實作計畫分階段完成。

### 2026-08-14 補充：收藏狀態自動流轉與成果雙軌建立

**狀態**：accepted

**討論內容**：使用者詢問收藏從「已收藏」排入行程後是否需要手動更新狀態，並確認成果展示除了系統提出候選、由使用者確認建立之外，也必須支援與其他模組無關的手動成果，例如「學會煮一道料理」。

**決策**：①收藏狀態原則上由實際操作自動推導，不要求使用者另行編輯狀態；加入行程後自動呈現「已加入行程」，完成實際造訪後自動呈現「已造訪」。取消收藏及確認是否實際造訪仍由使用者操作。②成果卡片採雙軌建立：系統依既有資料提出成果候選，使用者確認後建立；使用者亦可隨時手動新增不依賴其他模組的成果。

**理由**：若要求使用者先執行「加入行程」，又再手動修改狀態，會形成重複操作且容易失同步。成果來源不限於 App 可量化資料，因此不能只靠系統候選。

**後果**：收藏的顯示狀態需由行程關聯與造訪紀錄推導，不能只依賴可任意修改的單一狀態字串；成果資料需保存 `manual`／`suggested` 等建立來源。實際造訪確認方式與成果候選規則仍待後續確認。

### 2026-08-14 補充：行程預估支出、成果確認與刪除能力

**狀態**：accepted

**討論內容**：使用者確認旅遊行程需要填寫預估支出並與既有記帳功能結合；目標完成時系統只能詢問是否記錄至成果展示，不得自行建立成果；收藏清單與成果展示都必須允許使用者刪除。

**決策**：①旅遊行程保存預估支出，實際支出仍以既有記帳資料為唯一來源，透過行程關聯彙總，避免同一筆金額重複保存。②系統偵測目標完成後建立的是「成果候選」，必須由使用者確認後才建立正式成果卡片，拒絕時不得新增。③收藏與成果皆提供刪除操作。

**理由**：預估支出與實際記帳用途不同，分開保存才能比較預算與實際花費；成果屬於使用者對人生事件的主觀認定，系統不得代替使用者直接發布；使用者必須保有資料移除權。

**後果**：行程頁需呈現預估／實際／差額；成果候選需具備確認與拒絕狀態。收藏若已被行程或探索歷史引用，以及成果刪除採軟刪除或永久刪除的具體規則，仍待確認後定案。

### 2026-08-14 補充：預算粒度與刪除保護確認

**狀態**：accepted

**決策**：①行程預估支出支援交通、住宿、飲食、門票、購物、其他等分類並自動加總，也允許使用者只填預估總額；實際支出一律由關聯記帳資料彙總。②收藏與成果刪除前二次確認、刪除後提供 5 秒復原並防止連點。③未加入行程且無造訪的收藏可直接刪除；已加入未完成行程時提示並同步移除行程關聯；已有造訪紀錄時只刪除原始收藏，探索歷史快照保留。④刪除成果卡片不影響產生成果的原始資料。

**後果**：預算與實際支出不重複保存；歷史探索與原始生活資料不因刪除展示卡片而被連帶破壞。

### 2026-08-14 補充：收藏欄位、行程關聯與完成流程確認

**狀態**：accepted

**決策**：①收藏保留名稱、類型、國家、區域／城市、地址、參考網址、預估費用與備註；名稱、類型、國家及區域／城市必填，地點類收藏的地址必填，非地點活動可不填地址且不顯示於探索地圖；移除優先程度、縣市與想去日期。②同一收藏可加入多個旅遊行程，每趟行程各自保存實際造訪結果。③行程保留名稱、選填的開始／結束日期、國家、區域／城市、收藏項目及其顯示順序、預估支出與備註；規劃中可不填日期，確認或完成前必填；日期自動換算當天或 N 天 N 夜，不提供第幾天與時間點的細部排程。④行程完成時顯示收藏勾選清單，只為實際造訪項目建立探索紀錄，未造訪項目保留於收藏；未加入行程的收藏亦可直接標記已造訪。

**後果**：旅遊行程定位為收藏集合而非逐時旅遊規劃器；收藏狀態由行程關聯及造訪紀錄自動推導。

### 2026-08-14 補充：探索歷史與成果候選規則確認

**狀態**：accepted

**決策**：①同一地點在探索地圖只顯示一個標記，點開後列出各次獨立造訪；每次造訪可各自編輯日期、備註或刪除。②造訪時保存收藏名稱、類型、國家、區域／城市、地址、經緯度、備註、造訪日期與關聯行程快照，原收藏日後修改或刪除不影響歷史。③地址無法定位時仍可保存造訪紀錄，列入「無法定位」清單，待使用者修正地址後重新定位，系統不得猜測座標。④成果展示同時提供手動新增與待確認成果；系統候選第一階段只採體態達標、考試達標、運動累積、探索地點／國家數、行程完成及待辦里程碑，不以飲食或心情自動判斷。⑤成果保存必填名稱、完成日期及類別，選填說明、照片與關聯紀錄，並保存 manual／suggested 來源。⑥拒絕候選後不再重複詢問相同成果，但不同級距仍可另提候選。

**後果**：探索紀錄成為不可被原收藏意外改寫的歷史事件；系統只能提出可驗證的成果候選，正式成果仍由使用者決定。

### 2026-08-14 補充：支出、幣別、行程狀態、資料權限與入口定案

**狀態**：accepted

**決策**：①記帳新增選填的關聯旅遊行程，不限制交易日期必須落在行程期間；行程彙總預估支出、實際支出、差額及各記帳類別。②第一階段所有預估與實際支出統一使用新台幣，海外消費由使用者輸入換算後金額，不做匯率與多幣別。③行程狀態依操作流轉為規劃中、已確認、已完成、已取消；取消不刪收藏或記帳，並保留支出關聯及取消標示。④收藏、行程、探索與成果預設為個人資料，使用者只能管理自己的資料，Robin 不代改家人資料；第一階段不做共享行程或家庭共同編輯。⑤首頁收藏清單提供新增收藏，探索地圖只查看，成果展示提供新增成果及待確認提示；旅遊行程不設首頁卡片，從收藏清單進入建立／管理。左側選單保留收藏清單、探索地圖與成果展示，定位為查看、篩選與分析入口。

**理由**：維持記帳單一金額來源與第一階段功能邊界，避免引入匯率、共同編輯及額外首頁卡片造成不必要複雜度。

**後果**：使用者已於 2026-08-14 明確確認正式排入開發；需求已升級至 SPEC FR-73～FR-76a，並由 PROGRESS Phase 5 追蹤。

## 2026-08-14 [標籤：使用者] 收藏地點選擇、長清單與行程整合調整

**狀態**：accepted

**背景**：收藏定位 fallback 與收藏卡片操作修復完成後，使用者進一步檢視收藏、旅遊行程與探索地圖的實際操作，發現定位說明不足、地點欄位仍為自由輸入、長清單缺乏明確承載策略，以及旅遊行程尚未依目的地篩選收藏。探索地圖刪除亦在 Expo Web／PWA 發生無反應。

**討論內容**：①收藏表單上方需補充「目前定位功能以行政區／鄉鎮市區為主，可能無法精確辨識至門牌或街道」的限制說明。②國家與區域／城市採可搜尋、可選擇既有值且允許自行輸入新值的組合式下拉選單。③使用者所指的大量資料呈現是固定高度內容區塊搭配垂直捲軸；需在資料卡片區超過指定高度後只捲動該區塊，而不是無限制撐長整頁。後端是否再加分頁屬效能層議題，可依實際資料規模另外處理。④探索地圖刪除仍使用 Expo Web 不可靠的 Alert.alert 多按鈕回呼，與先前收藏卡片按鈕無反應屬同類問題。⑤單一旅遊行程只允許一個國家與一個區域／城市，收藏項目必須依該目的地過濾並改為下拉選擇；目前行事曆尚未套用共用的休假日、節日及重要日子資料。

**決策**：①國家與區域／城市採可搜尋、可選擇既有值且允許自行輸入新值的組合式下拉選單。②單一旅遊行程只允許一個國家及一個區域／城市，收藏下拉選單只顯示相同目的地的收藏。③旅遊行程提供「同步至重要日子」開關且預設開啟；開啟時建立與行程名稱、起訖日期連動的一次性重要日子，後續修改行程同步更新，取消或刪除行程時停用連動事件而非永久刪除。④行程行事曆同時顯示既有休假日、節日與重要日子，供使用者辨識日期衝突。

**決策補充**：⑤同步建立的重要日子預設提前 1 天提醒、通知對象為自己、顯示於待辦行事曆；使用者可在新增／編輯行程時自行調整提醒天數、通知對象與是否顯示於待辦行事曆。修改行程時保留既有提醒設定，不重設預設值；關閉同步時停用連動的重要日子及提醒。⑥收藏、旅遊行程、探索紀錄與成果展示等持續累積的卡片清單採最大高度 `60vh` 的內層垂直捲動區；組合式下拉選單最大高度 240px，超出後於選單內捲動。Web 顯示固定捲軸，iOS／Android 依系統行為在捲動時顯示捲動指示器。

**狀態更新**：上述需求已完成確認，可升級至 SPEC FR-73～FR-75 並排入實作。

**後果**：確認後需同步調整 SPEC FR-73～FR-75、Mobile 收藏／行程／探索 UI、行程收藏篩選、行事曆資料載入及必要的 API 分頁參數；探索刪除 Bug 另記 debug ADR。
## 2026-08-14 [標籤：使用者] 明確日期目標同步至重要日子

**狀態**：accepted

**背景**：旅遊行程已能把起訖日期同步成一次性重要日子。使用者進一步提出，記帳、體態、考試等模組若設定了明確目標日期，也應考慮採用同樣方式同步至重要日子設定。

**討論內容**：現有資料模型中，具備單一明確目標日期者為 `body_goals.target_date`（體重、運動、飲食）及 `certificate_goals.target_date`（考試／證照）；現行記帳只有月份預算，沒有單一完成日期，因此尚無可直接同步的事件日期。同步需確認適用範圍、是否預設開啟、提醒／通知對象預設值，以及目標更新、達成、取消或覆寫時的重要日子生命週期。

**決策**：①同步範圍為 `body_goals.target_date`（體重／運動／飲食）及 `certificate_goals.target_date`（考試／證照）；現行記帳僅有月份預算，沒有單一完成日，本階段不納入。②有日期的目標預設同步，預設提前 1 天、通知自己、顯示於待辦行事曆，使用者可在重要日子設定調整。③目標名稱或日期更新時同步更新並保留提醒設定；達成、取消或清除日期時停用連動事件。④不恢復已取消的 FR-69 Mobile 目標設定頁，目標仍由既有 Telegram 流程建立，Mobile App 負責顯示與管理同步後的重要日子。使用者於 2026-08-14 確認實作。

**理由**：避免把沒有明確日期的月份預算誤建成單日事件，也避免目標與重要日子產生重複或失效資料。

**後果**：新增 `0082` migration 連結目標與重要日子並回填既有具日期目標；目標建立／更新／達成／取消流程同步維護事件。Mobile 不另建立目標設定入口。
