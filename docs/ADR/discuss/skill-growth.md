# 個人技能成長（每日技術分享／TOEIC 證照題庫） 討論紀錄

## 2026-08-07 [標籤：AI] ADR-18：TOEIC 雙軌題庫 Pipeline（Step 3.2）三項設計決策

**狀態**：accepted

**背景**：Step 3.2 開工前經 AskUserQuestion 與 Robin 確認三個關鍵設計問題。

**決策**：①`gdrive` 擴大 OAuth scope 而非改走 Telegram 上傳——維持「直接把照片/音檔手動丟進 Google Drive 資料夾，機器人每週排程掃描」的工作流程，`gdrive` 新增 `list_files()`／`download_file()`，scope 擴大為 `drive.file + drive.readonly` ②整包聽力 MP3 自動切割這次一起做——切割邏輯用 Groq Whisper 逐句時間軸之間的停頓當候選切割點，是尚未經真實素材驗證的啟發式判斷（**同日追加驗證**：Robin 上傳真實錄音實測，發現原始版本會把開頭作答說明語音整段併入第一題，修正為先篩選掉句子內部小停頓雜訊，再逐一試切比較「每段長度變異數」，選變異數最小的一組，正確排除說明語音）③Step 3.2 範圍只到「建題庫」，每日推播/作答/批改功能明確留給 Step 3.3 ④（同日追加）`exam_type` 泛用化，不寫死證照種類清單——Robin 明確要求「不能鎖死這三類（TOEIC/GCP/AWS）」，檔名格式改為 `{exam_type}_{test_id}_write/listen_{題號}.{ext}`，`exam_type` 開放解析成任意字串。

**替代方案**：改用 Telegram 上傳（已否決，不符合原本設想的工作流程）；先只做「已切好的小檔案比對」（已否決，Robin 選擇效率優先，一次做完整）；一律在 Telegram 對話設定 `exam_type`（已否決，多一道手動設定步驟）。

**理由**：決策 1 符合 Robin 原本設想的使用情境；決策 2 一次把 Pipeline 做完整比分兩次交付更有效率，風險已提前告知並取得同意；決策 4 開放式字串解析成本低，符合「新增證照類型只換檔名前綴、不改程式碼」的目標。

**後果**：Robin 需要重新執行一次 `get_refresh_token.py`；整包 MP3 切割參數未來可能需要依實測結果調整；`exam_type` 沒有拼字檢查，打錯字會被當成新的證照類型獨立存在。

## 2026-08-07 [標籤：AI] ADR-19：Step 3.3（作答紀錄、成效追蹤與正式成績）設計決策

**狀態**：accepted

**背景**：Step 3.3 開工前經多輪對話與 AskUserQuestion 確認範圍與關鍵設計問題。

**決策**：①每日推播固定 08:00，比照 `skill_growth_digests` 排程模式 ②正解改用真實拍照，不用 AI 推論——Robin 選擇拍照上傳購買的測驗書正確解答（檔名 `{exam_type}_{test_id}_write/listen_{題號}_ans.png`）③缺正解的題目排除於每日推播候選池 ④成效查詢改為彈性文字問答，不做圖表——圖表視覺化統一交給 Phase 4 Mobile App ⑤錯題統計維度沿用既有欄位，不新增主題標籤 ⑥作答紀錄用一張統一表串連軌道一／軌道二（兩個可為 NULL 的外鍵＋CHECK 限制）⑦正式成績獨立建表。

**理由**：Robin 有現成的正確解答來源，比讓 AI 推論更準確；避免 Step 3.3 範圍蔓延到「重新設計 Vision 解析 Prompt 與題目主題分類系統」；一張表可以直接用單一 SQL 查出一段時間所有作答紀錄。

**替代方案**：沿用原規劃讓 Gemini Vision 推論正解（已否決）；軌道一/軌道二分開建兩張作答紀錄表（已否決，查詢會需要 UNION）。

**後果**：`certificate_questions` 新增 `correct_answer`／`explanation`／`answer_source_filename` 欄位；週排程掃描邏輯需要改為兩階段處理（先題目後正解）。

## 2026-08-08 [標籤：AI] ADR-20：Step 3.3 每日推播出題（FR-26）與作答（FR-27）細部設計

**狀態**：accepted

**背景**：ADR-19 定案 Step 3.3 整體範圍後，開工前針對「每日推播出題」「作答」互相牽動的功能，經多輪對話與 AskUserQuestion 進一步確認設計細節。

**決策**：①出題數量/比例依 `exam_type` 是否為 TOEIC 而不同——非 TOEIC 只能調每日出題數量，TOEIC 額外可調三軌比例 ②新題/複習題比例另開一個獨立維度（預設 7:3），複習池只放「最新一次作答結果是答錯」的題目 ③作答格式只接受回覆選項字母 A/B/C/D，不用 LLM 解析口語化回答 ④23:00 視為跳過採靜默處理 ⑤彈性排程支援四種語意（挪動/取消/區間覆蓋/平攤）⑥（2026-08-08 追加）「平攤」語意：Robinson 自行計算分攤方案，但不能直接寫入，必須先列出方案給 Robin 確認，Robin 同意才寫入，計算規則為從明天起連續每天 +1 題直到攤完，命中既有覆蓋日期則跳過。

**理由**：非 TOEIC 證照沒有軌道二可分配，沒有「比例」可言，現階段只有 TOEIC 有實際題庫；把「複習」跟「TOEIC 特有的三軌分配」拆成兩個獨立維度，邏輯更單純；「平攤」語意會一次動到多筆日期的資料，屬於「Robinson 自行運算後的建議」而非明確指令，寫入前一定要讓 Robin 看過具體會變動的日期與題數。

**替代方案**：現在就設計成通用規則（已否決，先服務實際存在的需求）；用 LLM 解析口語化回答（已否決，選擇題本來就適合固定格式回覆）；發送跳過通知（已否決，每天已經有 20:00 提醒，晚上再一則太多）。

**後果**：新增 `certificate_daily_settings`／`certificate_daily_schedule_overrides`／`certificate_daily_assignments` 三張表；彈性排程的四種語意需要比照待辦事項的自然語言解析模式處理，語意④「平攤」額外需要一個「提案—確認」多輪對話狀態機。

## 2026-08-09 [標籤：AI] ADR-25：`skill_growth_digests` 改為「一天多筆、一筆一個來源管道」正規化設計（取代原單筆合併 `summary_text`）

**狀態**：accepted（部分內容於 2026-08-09 同日再由 ADR-29 修正，見下方條目）

**背景**：Step 3.1 上線後，Robin 回報實際推播內容有兩個問題：①三個來源合併成單一 `summary_text` 欄位，完全無法分辨當天到底是哪個來源沒抓到內容 ②推播訊息把每則新聞整理成完整條列文章，內容太長，Robin 只需要三行式重點結論。

**決策**：①`skill_growth_digests` 新增 `source` 欄位（`tldr`／`ithome`／`techcrunch`），約束改為 `UNIQUE (digest_date, source)`，一天最多寫入三筆 ②推播訊息格式改為三行式 ③舊表直接 `DROP TABLE` 砍掉重建，不做資料搬遷（Robin 確認舊表當時僅有 1 筆資料）。

**理由**：Claude 原提案是新增 3 個獨立欄位取代 `summary_text`，被 Robin 否決——理由是未來每新增一個來源就要 `ALTER TABLE` 加欄位，擴充性差；改成 `source` 欄位＋正規化多筆列的設計，新增來源只需要多寫一個 `source` 值。

**替代方案**：3 個獨立欄位（已否決，見上方理由）；就地 `ALTER TABLE` 加 `source` 欄位、保留舊資料為 legacy 列（Claude 原提案，Robin 認為多此一舉）。

**後果**：三個來源各自獨立呼叫 Gemini（一次收集最多 3 次 API 呼叫，取代原本 1 次）。

## 2026-08-09 [標籤：AI] ADR-29：每日技術分享改回深入摘要、拆成三則獨立訊息，並修正 IThome RSS 解析 bug（supersede ADR-25 訊息格式部分）

**狀態**：accepted

**背景**：ADR-25 把每日技術分享改成「三行式精簡結論」，是為了讓 Robin 能分辨哪個來源異常。但 Robin 實測後回饋「現在這樣寫說實話我也學不到什麼，因為寫得太淺了」，並指出「iThome 在 8/8 有發表一篇 CVSS 9.8 重大漏洞的文章，為什麼沒抓到？」。經比對 Robin 提供的實際 RSS 內容，發現 IThome 的 `<pubDate>` 格式非 RFC 822 規格（純日期時間、無時區），`submodules/newsfeed` 只用標準格式解析，導致 IThome 每一篇文章都在解析日期這一步被跳過——這才是每天顯示「今日無內容」的真正原因，不是真的沒有新聞。Robin 也指出過去只用標題/連結生成摘要，等於在編造沒看過的文章內容（「只看標題我也會啊？」），要求真的抓全文。

**決策**：①修正 IThome `<pubDate>` 解析 bug，新增 fallback 格式 ②IThome／TechCrunch 改為抓取文章全文（`fetch_article_content()`，用 `requests` + `beautifulsoup4`，刻意不寫死站台專屬 selector）③摘要深度改回「列點＋總結」格式，拿掉 100 字內的長度上限 ④推播拆成三則獨立 Telegram 訊息，當天沒有內容的來源直接不推播那則訊息，三個來源全部都沒有內容才維持「未獲得最新技術分享」固定訊息。

**理由**：決策 1 是確切驗證到的 bug，沒有替代方案；決策 2 只給標題會逼 Gemini 編造內容，違反專案一貫「不可幻覺」原則；決策 3 跟 ADR-25 的方向直接相反，但這是 Robin 實測後的第一手回饋，兩個問題本質不同，per-source 正規化設計仍然有效、不需要更動；決策 4 讓訊息量更精簡，Robin 一眼就能看出今天有哪些來源真的有新東西。

**替代方案**：改用讀者可讀性演算法（`readability-lxml`／`trafilatura`）取代手動抓取（已考慮但未採用，多一個較重的第三方依賴，目前只有兩個已知來源，手動啟發式規則足以應付）。

**後果**：`requirements.txt` 新增 `beautifulsoup4`；Gemini Token 用量增加（全文比標題長很多），仍在免費額度內；收集階段執行時間變長，仍在 `/healthz` 單一小時窗口內可接受。

## 2026-08-08 [標籤：AI] `language`（語言學習）功能規劃暫時擱置，不排入目前 Roadmap（原記錄於 robinson SPEC.md ADR-23）

**狀態**：accepted

## 2026-08-14 [標籤：使用者] 非 TOEIC 證照正式導入與驗收暫時擱置

**狀態**：accepted

**背景**：既有證照題庫已將 `exam_type` 泛用化，題庫 Pipeline、每日出題數量、新題／複習題、作答紀錄與正式成績資料結構也能承接非 TOEIC 類型；但目前只有 TOEIC 有實際題庫與完整操作驗證，`DRAFT.md` 尚未記錄非 TOEIC 證照後續工作狀態。

**討論內容**：盤點現況後確認，非 TOEIC 並非從零建立共用系統，而是針對實際目標證照導入題庫素材、確認題型差異、設定推播／作答規則並完成端到端驗收。

**決策**：非 TOEIC 證照題庫正式導入與驗收列為擱置中，不排入目前 Roadmap；既有泛用資料結構與解析能力維持不變。未來確定實際證照類型後，先確認題型、素材命名、正解來源、每日出題方式與成效判定，再升級為正式規格。

**理由**：目前沒有明確的非 TOEIC 目標證照與實際題庫，提前設計證照專屬規則容易形成假設性開發；保留既有泛用底座即可降低未來導入成本。

**後果**：`docs/specs/DRAFT.md` 新增擱置索引；清點剩餘工作時需將此項標示為擱置，不得誤報為尚未完成的 Phase 3 主線，也不得把既有泛用支援誤記為完整非 TOEIC 功能已上線。

## 2026-08-18 [標籤：使用者] ADR-31：考試設定選單化與證照名冊

**狀態**：accepted

**背景**：Owner 主選單仍顯示「📖 考試成績」且只回覆開發中；既有證照目標、每日出題、區間覆蓋、正式成績與成效邏輯雖已存在，入口仍倚賴已取消的文字／Slash Command 流程。另有兩個資料缺口：新建但尚無目標、成績或題庫的自訂證照無法穩定顯示，以及正式成績沒有補充內容欄位。

**決策**：①主選單改名「📖 考試設定」，Owner 專屬且所有 Callback 在後端重新驗證權限；子選單固定為證照設定、目標、每日題數設定、實際考試紀錄。②新增 Owner 專屬證照名冊，TOEIC 預設存在；其他證照經名稱輸入、摘要與按鈕二次確認後建立。自訂證照可停用但不實體刪除，歷史目標、設定與成績仍保留。③尚無題庫的自訂證照可建立目標與正式成績；每日題數設定必須明確告知不會推播。④TOEIC 每日設定改以固定聽力／讀寫／單字題數保存，總題數自動加總；其他證照只有每日總題數。⑤日期區間覆蓋不允許重疊，提供建立、查看、編輯與二次確認刪除；0 題代表停出。⑥正式成績新增選填補充內容，仍只允許新增與查詢，不提供修改或刪除。

**理由**：名冊讓尚未有任何其他資料的證照仍能出現在設定流程；停用取代刪除可保留正式成績與目標歷史。固定題數符合 Robin 直接指定三種 TOEIC 題型各出幾題的操作心智模型；禁止區間重疊可消除現有查詢遇到多筆命中時的優先順序不確定性。

**後果**：需新增向前相容 migration 建立名冊、補充內容及 TOEIC 固定題數欄位，並回填既有 Owner 的 TOEIC 與既有 `exam_type` 資料；舊文字／Slash Command 證照入口不保留相容期。非 TOEIC 題庫實際導入與驗收仍維持擱置，見上方 2026-08-14 決策。

**實作結果**：新增 `src/bot/certificate_settings.py` 與 migration `0091`；所有寫入包含自訂證照啟停、目標、全局／區間題數、正式成績與區間刪除，均採摘要後按鈕確認。日期區間在輸入與確認兩階段檢查重疊，資料庫再以 exclusion constraint 防止競態；變更或刪除涵蓋今天的區間時，會清除今天尚未作答的指派以便重新依有效設定產生。

## 2026-08-25 [標籤：使用者] ADR-32：聽力題目庫改版——整包音檔 cutoff、解答照片統一驅動、聽力題禁止顯示文字

**狀態**：accepted

**背景**：Robin 打算把整份 ~45 分鐘的 TOEIC 聽力測驗錄音直接上傳，但現有整包音檔切割邏輯（`_find_split_plan()`）假設「1 題 = 1 段長度大致相等的獨立音檔」，只適用於 Part 1（照片描述）與 Part 2（問答），不適用於共用一段對話/短文音檔、每 3 題一組的 Part 3／4。Robin 明確表示只想自動切 Part 1+2，忽略後面的 Part 3+4。討論過程中經多輪對話與 AskUserQuestion 進一步釐清三種可能的上傳情境（整份聽力整包／單一 Part 整包／單一 Part 單題已切好的音檔），並確認不同 Part 一定來自不同場考試（不同 `test_id`），檔名不會衝突。

過程中進一步發現一個更根本的設計缺陷：Part 2 是純聽力，完全沒有印刷內容可拍照，但既有設計要求「一定要有題目照片才能建題」，導致 Part 2 永遠無法建題。Robin 提出改用「解答照片」（測驗書的解答/詳解頁，本來就會印出原始題目/選項逐字稿）作為聽力題內容的統一來源，題目照片改為純顯示用（例如 Part 1）。

這又牽出一個真正的資料風險：`certificate_questions.image_gdrive_url` 是 `NOT NULL`，且在作答時會顯示給使用者看（`certificate_answer.py` 的「🖼️ 題目圖片」）。若沒有題目照片時 fallback 顯示解答照片，會在使用者作答前就洩漏正解圖片，被 Claude 主動提出並向 Robin 說明後暫緩。

最後 Robin 進一步釐清各 Part 的正確呈現方式，指出既有的 `_build_certificate_question_view()` 顯示邏輯本身就是錯的——目前不分聽力/閱讀，一律把 `question_text`／`options` 文字顯示出來，這對聽力題完全不符合考試情境（Part 1 只能看圖用聽的作答；Part 2 什麼都不顯示、純聽力；只有閱讀 Part 5 才應該顯示文字題目與選項）。

**決策**：①整包聽力音檔檔名新增選填後綴 `_cutoff{秒數}`，只切割/處理指定秒數之前的內容（`_split_whole_audio()` 依 `cutoff_seconds` 先用 `pydub` 裁切音檔、再過濾逐字稿分段時間戳記）②聽力題（所有 Part）內容改由「解答照片」（`_ans`）統一驅動一次性建題（題目文字／選項／正解／詳解皆來自同一張解答照片的 Vision 解析，新增 `_LISTEN_ANSWER_VISION_PARSE_PROMPT`），題目照片（`listen_images`）改為選填，只用於顯示，不再是建題必要條件；`_process_answer_keys()`（原本「先建題後補正解」兩階段流程）限縮為只處理 `write`（閱讀）類型，聽力題改為一階段直接建立 ③`certificate_questions.image_gdrive_url` 改為 nullable（migration `0099`），避免用解答照片 fallback 造成洩題風險——沒有題目照片就是 `NULL`，不顯示圖片區塊 ④`_build_certificate_question_view()` 依 `question_type` 分流：`listen` 完全不顯示 `question_text`／`options` 文字，只顯示題目圖片（有的話，例如 Part 1）與聽力音檔連結；`write`（閱讀）維持原行為，照樣顯示文字題目＋選項。

**理由**：`_cutoff` 後綴是最小侵入的解法，不需要額外的上傳介面或資料表，符合現有「檔名驅動」的一貫慣例；解答照片本來就有完整逐字稿，用它統一驅動聽力題內容，比要求 Part 2 也拍不存在的「題目照片」更貼近現實；把 `image_gdrive_url` 改 nullable 並嚴格區分「有沒有圖片」而非「fallback 成解答圖」，從資料層面直接杜絕洩題風險，比僅在顯示邏輯加判斷更安全；顯示邏輯依 `question_type` 分流，才真正符合真實考試的作答情境（聽力題只能靠聽的），修正前的「一律顯示文字」設計會讓聽力題失去測驗意義。

**替代方案**：整包音檔額外要求 Robin 手動先剪好只含 Part 1+2 的音檔再上傳（已否決，Robin 希望直接丟整份錄音，減少人工前處理）；沒有題目照片時 fallback 顯示解答照片充當題目圖（已否決，會在作答前洩漏正解）；`image_gdrive_url` 維持 `NOT NULL`、改用空字串或佔位圖代替（已否決，語意不清楚，也無法乾淨地在顯示邏輯區分「真的沒有圖」與「資料異常」）。

**後果**：新增 migration `0099_make_certificate_questions_image_nullable.sql`；`docs/reference/db_schema.md` 同步更新 `image_gdrive_url` 為 nullable 並註明來源 migration；`src/bot/toeic.py` 檔名比對正則（`_FILENAME_PATTERN`）新增選填 `cutoff` 群組，`parse_filename()`／`classify_drive_files()` 回傳結構隨之調整；既有依賴「聽力題一定有題目照片」的假設全面移除，未來若新增 Part 3/4 的整段共用音檔自動切割，仍需另外設計（目前僅止於用 `_cutoff` 排除，不主動處理）。
