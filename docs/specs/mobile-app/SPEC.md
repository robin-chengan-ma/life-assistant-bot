# 羅賓森 Mobile App

## 概要

對應 [robinson SPEC.md](../robinson/SPEC.md) Phase 4 Step 4.4／4.5（FR-64～FR-72，見 ADR-28）。本文件收納 App 各頁面的詳細內容規劃：首頁卡片邏輯、各模組唯讀分析頁面呈現方式、全域 UX 規則。登入機制、權限矩陣、可編輯設定頁面的欄位範圍已在 robinson SPEC.md FR-65～FR-72 定案，本文件不重複列出，只在需要新增細節時補充。**目前仍為規劃階段，尚未開工實作**，本文件內容會隨與 Robin 的討論持續調整。

## 首頁（Dashboard）

點擊左上選單「首頁」（固定排在選單第一項）或登入後預設進入的頁面。除「重要通知」卡片外，其餘卡片點擊皆直接跳轉對應模組的唯讀分析頁面，是選單之外的第二個進入路徑。

**首頁只放全體使用者共用的模組（2026-08-10 定案）**：求職分析／考試成績／技術分享／客訴回饋這四個模組目前僅 Robin 一人可用（`owner_only`），不需要在首頁另外放卡片佔位置，直接放在左上選單即可進入；首頁卡片區塊只呈現待辦事項／記帳分析／體態管理（飲食/運動/體重）／心情趨勢這幾個全體使用者共用的模組，維持首頁對一般使用者的簡潔度，也不用為了 4 個只有 Robin 看得到的模組另外處理「一般使用者看不到這些卡片」的權限判斷。

| 卡片 | 有資料時 | 沒資料時 | 可點擊 |
|---|---|---|---|
| 重要通知 | 顯示當天推播給該使用者的通知文案（可能不只一則，全部列出；文案內容見 robinson SPEC.md FR-53f／ADR-30） | 「今日無重要通知」 | 否，純顯示卡片，不連結任何頁面 |
| 待辦事項 | 「今日有 N 件待辦事項」 | 「今日有 0 件待辦事項」（0 本身是合法狀態，不算「沒資料」） | 是 → 待辦事項頁 |
| 記帳分析 | 「今日已花 N 元」 | 「今日尚未記帳」 | 是 → 記帳分析頁 |
| 飲食紀錄 | 「今日已吃 N1 克脂肪、N2 克蛋白質、N3 克碳水化合物、共 N4 大卡，喝 N5 毫升水」 | 「今日尚未記錄飲食」 | 是 → 體態分析頁（飲食分頁） |
| 運動紀錄 | 「今日透過 {活動1}、{活動2}… 消耗 N 大卡」（同一天有多筆不同活動時全部列出活動名稱、卡路里加總，例如「今日透過慢跑、重訓消耗 320 大卡」） | 「今日尚未記錄運動」 | 是 → 體態分析頁（運動分頁） |
| 體重紀錄（2026-08-10 新增） | 「目前體重為 N 公斤」（取 `body_weight_logs` 最新一筆，不限「今天」——體重不像飲食/運動需要每天記錄，見下方說明） | 「尚未紀錄過體重」 | 是 → 體態分析頁（體重分頁）；卡片內另有獨立「開始量測」按鈕，見下方說明 |
| 心情趨勢 | 直接顯示當天最新一筆心情小記的內容（同一天多筆只顯示最新一筆） | 「今天想記錄一下心情嗎」 | 是 → 心情趨勢頁 |

**卡片命名（2026-08-09 修正）**：沿用 Robin 原描述的「飲食紀錄」／「運動紀錄」兩張獨立卡片名稱（先前文件誤寫成「體態分析（飲食／運動）」，已修正），資料分屬 `diet_logs`／`exercise_logs` 兩張表、語意也不同，拆成兩張卡片符合「一張卡片一個獨立資訊」的原則；兩張卡片點擊都導向同一個「體態分析」頁面，只是進頁面後預設分頁不同。

**體重紀錄卡片（2026-08-10 新增）**：與「飲食紀錄」／「運動紀錄」同屬體態管理的一部分、同樣導向「體態分析」頁面（體重分頁），但顯示邏輯不同——飲食/運動卡片是「今日有沒有記錄」，體重卡片改成「最新一筆是多少」，因為體重通常不會每天量，用「今日尚未記錄」的邏輯會讓卡片經常空白、失去參考價值；改成「顯示最新一筆（不限今天）」＋「完全沒紀錄過才顯示尚未紀錄」，隨時都能看到目前體重。卡片內建一個「開始量測」按鈕，點擊直接觸發 FR-64a 的藍牙掃描流程（**沿用 FR-64a 既有設計，同時把該條文原本的按鈕名稱「開始測量」統一改為「開始量測」，避免同一功能出現兩種按鈕文案**），10 秒內量到體重就寫入 `body_weight_logs` 並即時更新卡片文字，量不到則維持原文字不變並提示「未取得您的體重值」；按鈕本身是卡片內的獨立可點擊區域，點擊卡片其餘區域（非按鈕處）才是導向體態分析頁的既有行為，兩者互不干擾。人不在家、沒帶體重計時仍可以走 Telegram 既有 `/log_weight` 流程手動輸入，兩種入口寫入同一張表，卡片會反映最新一筆，不分入口。

### 首頁圖表預覽區（2026-08-09 新增並定案）

首頁卡片區塊下方，放一個帶頁籤的趨勢圖預覽區塊，固定 5 個頁籤：**記帳、體重、飲食、運動、心情**，每個頁籤各自顯示該模組的迷你趨勢圖（沿用對應模組唯讀分析頁的同一份圖表資料，只是縮圖版本），切換頁籤即時換圖，不用跳頁。點擊圖表可跳轉到對應模組的完整分析頁面看細節。

**範圍說明**：只涵蓋全體使用者共用的 5 個模組（對應「體態分析」拆出的體重／飲食／運動三個子類型＋記帳＋心情）；求職分析／考試成績／技術分享／客訴回饋（Robin only 四個模組）不放進首頁圖表預覽區——這四個模組本來就不在首頁（見上方「首頁只放全體使用者共用的模組」），只透過左上選單進入各自的唯讀分析頁面查看細節。

## 左上選單（Drawer）與導覽

依 [robinson SPEC.md FR-67a](../robinson/SPEC.md) 權限矩陣，固定顯示順序：**首頁**、待辦事項、體態分析、記帳分析、心情趨勢、求職分析（Robin only）、考試成績（Robin only）、技術分享（Robin only）、客訴回饋（Robin only）。「首頁」為 2026-08-09 追加的第一項。求職分析／考試成績／技術分享／客訴回饋這四個 Robin only 模組**只透過選單進入**（2026-08-10 定案，見上方首頁章節），不像其他模組同時有「首頁卡片」這個第二進入路徑。

## 視覺風格（2026-08-09 提案，Robin 初步認可，細節持續調整中）

- **色彩**：主色用青綠（沉穩、不商務），強調色用暖橘（提醒/正向數據），中性灰做背景與次要文字；深色模式沿用同一套色相、僅調整明暗，不用另外設計一套配色
- **模組辨識色**：每個模組固定一個辨識色，用在選單小圖示與卡片點綴。全體共用模組：記帳＝橘、體態＝綠、待辦＝藍、心情＝粉紫。**Robin only 模組（2026-08-10 定案，Robin 授權由 Claude 決定，日後覺得需要調整會再提出）**：客訴回饋＝中性灰（既有）、求職分析＝紫（呼應「職涯發展/專業」的既有色彩聯想）、考試成績＝琥珀（金榜/成就感的暖色調，跟證照分數的正向意義相符）、技術分享＝紅（三個 Robin only 模組裡唯一偏暖的醒目色，跟「即時技術快訊」的資訊時效性做出區隔；沿用既有 9 色 CDS 色板，青綠已作為 App 主色，刻意不重複用在單一模組上，保留給整體品牌識別）
- **卡片樣式**：圓角、留白足夠、線性圖示＋標題＋數字三段式結構，重要通知卡片用淺色底做出「純顯示、不可點」的視覺區隔
- **圖表樣式**：目標值一律虛線淺灰、實際值用該模組辨識色的實線；缺值處直接斷線（見下方全域 UX 規則），不畫花俏的漸層或陰影
- **首頁圖表預覽**：記帳/體重/飲食/運動/心情五個頁籤的迷你趨勢圖固定放在首頁卡片區塊下方（見上方「首頁圖表預覽區」），Robin only 四個模組不在此列

## 全域 UX 規則

- **圖表時間範圍**：所有唯讀分析頁面的趨勢圖預設顯示「過去一週」，使用者可自行篩選，最長開放到「過去一個月」；篩選變動時圖表即時重繪，不需要按查詢按鈕
- **缺值處理**：篩選範圍內若某天沒有資料，折線圖在該處直接斷開，不與前後資料點連成一條線（避免誤導成「當天數值是 0」或用內插值填補）
- **功能關閉**：若使用者把某模組的功能開關（FR-70）關閉，該模組在選單（以及有首頁卡片的模組，額外含首頁卡片）仍會顯示，但整塊呈現灰底樣式；點擊灰底區塊跳出「請先把功能打開才能使用喔」提示，不進入頁面。求職分析／考試成績／技術分享／客訴回饋這四個 Robin only 模組沒有首頁卡片（見上方首頁章節），此規則對它們只套用在選單項目上
- **完全無資料（從未使用過）**：功能開啟但資料庫裡完全沒有任何一筆紀錄，頁面顯示「未找到任何一筆資料！」
- **篩選範圍內無資料（曾用過，但這段時間沒有）**：跟上一點文案分開，顯示「這段期間沒有任何紀錄」，避免使用者誤以為自己從沒用過這個功能（**2026-08-09 補充**：Robin 原描述沒提到這個情境，Claude 盤點時發現需要跟「完全沒用過」區分）
- **錯誤訊息**：一律去技術化（比照 robinson SPEC.md NFR-6），不顯示 API 錯誤細節或路徑

## 各模組唯讀分析頁面

### 待辦事項

以行事曆檢視呈現（月曆格子，當天有待辦事項的日期打點/標記，點擊該天展開清單）。

**與 Google Calendar 整合（robinson SPEC.md FR-66）的關係（2026-08-09 釐清）**：App 行事曆檢視只是「待辦事項」模組資料的其中一種呈現方式，資料來源仍是同一份 `todos` 表，不是另一份真相來源；Google Calendar 整合服務的是「不開 App、直接用手機原生行事曆看」的情境，兩者互補、不重複。App 端不額外開發「把 App 內待辦寫入手機原生行事曆」的功能——這個需求已由 FR-66 涵蓋（家人訂閱共用行事曆即可看到），重複做容易造成同一筆待辦在原生行事曆上出現兩次或不同步。

### 體態分析

分頁呈現三種類型，各自獨立的趨勢圖：

| 分頁 | 圖表 | 說明 |
|---|---|---|
| 體重 | 體重趨勢折線圖（體重值／目標值兩條線） | 目標值取自 `body_goals`（`goal_type='weight'`）的 `target_value`；沒有設定目標時只畫體重值一條線 |
| 體重 | BMI 趨勢折線圖（BMI 值／目標 BMI 兩條線） | BMI 值 = 體重 ÷ 身高(m)²，即時計算、不落地存欄位；目標 BMI = 目標體重 ÷ 身高(m)²；使用者沒填身高（`users.height_cm` 為 NULL）或沒設定體重目標時，只畫 BMI 值一條線（正常情境，非空狀態） |
| 飲食 | 五大成分趨勢圖（水、脂肪、卡路里、碳水化合物、蛋白質） | 對應 `diet_logs` 依日彙總 |
| 運動 | 運動趨勢圖（每日消耗卡路里／累積分鐘數） | 對應 `exercise_logs` 依日彙總；有設定運動目標（`goal_type='exercise'`）時疊加目標線 |

### 記帳分析

| 圖表 | 內容 |
|---|---|
| 支出趨勢 | 折線圖，X 軸日期、Y 軸每日/每週支出金額 |
| 支出分類 | 圓餅圖，依 `transactions.category`（餐飲/交通/購物/居住/娛樂/醫療/其他）加總佔比 |
| 收支比較 | 收入／支出雙線折線圖同框比較；收入類別（薪資/獎金/其他）種類少，不畫圓餅圖，改在圖表下方用文字列出「本期收入合計 $X（薪資 $A、獎金 $B、其他 $C）」 |

### 心情趨勢

心情趨勢圖（依 `mood_journals.mood_category` 六種分類隨時間變化呈現），下方用多個卡片列出篩選範圍內每一筆心情小記的內容（`content`／`achievement_note`）。

### 求職分析（Robin only）

1. 應徵漏斗：已應徵 → 已獲得面試 → 已拿到 Offer／未錄取或已婉拒，各狀態職缺數量
2. 契合度分數分布：80～100 高度推薦／60～79 可考慮／60 以下較不合適，三個區間各自職缺數量
3. 本期 Top 推薦清單：職稱、公司、分數、推薦理由摘要，可展開看技能缺口說明（`job_postings.recommend_reason`／`skill_gap_note`）
4. 應徵歷程時間軸：依時間列出每個職缺的狀態變化（`job_applications`）

### 考試成績（Robin only）

1. 各證照目標進度卡片：目標日期倒數天數、目標分數/合格門檻（`certificate_goals`）
2. 正式成績歷程：`exam_official_scores`，同一證照類型考過多次時依時間呈現（`score` 為數字可畫趨勢線，若為「通過/未通過」等非數字文字則改列表呈現）
3. 每日練習正確率趨勢：依 `answer_logs` 算每日/每週正確率折線圖，可依證照類型/題型（write/listen/vocab）切換
4. 弱點分析：依題型統計哪個類型錯最多

### 技術分享（Robin only）

**2026-08-09 確認範圍**：同時涵蓋「每日技術摘要」（`skill_growth_digests`，TLDR／iThome／TechCrunch 三個來源）與「YouTube 技術情報週推播」內容，同一頁呈現（可依時間或來源分區塊）；YouTube 推播內容只顯示標題與推薦理由摘要，不顯示可點擊的影片連結——真的想看影片仍需回 Telegram 推播訊息裡點連結。

### 客訴回饋（Robin only）

**2026-08-09 修正為兩個區塊**（Robin 釐清後修正，取代本文件先前「單一列表＋解法欄位」的初版設計，見下方 ADR-1）：

| 區塊 | 資料來源 | 內容 | 是否可編輯 |
|---|---|---|---|
| 使用者客訴 | `complaints`（robinson SPEC.md FR-60～FR-63，使用者主動觸發） | 依時間倒序列出：日期、客訴內容 | 否，純查看 |
| 系統錯誤回報 | `system_error_reports`（robinson SPEC.md FR-19j，系統例外自動記錄） | 依時間倒序列出：發生時間、分級（一般感冒級／重大疾病級）、錯誤摘要、解法（`resolution`，尚未處理則留白） | 僅「解法」欄位可編輯，其餘唯讀 |

兩者是完全不同的兩張表、兩種性質（使用者主動回饋 vs. 系統主動通報），只是共用同一個「客訴回饋」App 選單入口分頁呈現。

## 設計決策

### ADR-1：「客訴回饋」頁拆成「使用者客訴」與「系統錯誤回報」兩區塊，「解法」欄位只加在系統錯誤回報

**背景**：Robin 詢問客訴回饋的觸發機制，本文件初版誤將「解法」欄位設計加在 `complaints`（使用者客訴）上。Robin 後續澄清：使用者主動送出的客訴內容他只是查看，不需要解法欄位；真正需要追蹤處理進度、需要「解法」欄位的是系統主動推送給他的錯誤回報（NFR-8／FR-19b 既有機制），因為這些他需要實際處理系統才能正常運作。Robin 同時要求解法的記錄不能只能在 App 操作，Telegram 也要能下指令記錄。

**決策**：
1. 「客訴回饋」頁拆成「使用者客訴」（`complaints`，純唯讀）與「系統錯誤回報」（新表 `system_error_reports`，見 robinson SPEC.md FR-19j，含 `resolution` 欄位）兩個區塊，`complaints` 表不新增任何欄位（修正本文件先前的錯誤提案）。
2. `system_error_reports` 的 `resolution` 欄位同時支援 App 與 Telegram 兩種入口寫入：App 端在系統錯誤回報卡片直接編輯；Telegram 新增 Owner 專屬單行指令「錯誤ID=N 已處理：{解法內容}」（見 FR-19j）。兩個入口呼叫同一支 service 層函式，不重複開發。
3. `_notify_robin_of_error()`（`webhook.py`）於既有流程中新增一步：把這次錯誤寫入 `system_error_reports` 並取得序號，私訊 Robin 時附上「錯誤ID=N」，讓 Robin 知道要用哪個 ID 下指令記錄解法。

**理由**：
- 決策 1：使用者客訴與系統錯誤回報服務的目的完全不同——前者是「聽取意見」，後者是「系統維運追蹤」，混在同一張表、同一種可編輯規則裡會讓語意不清楚，拆開資料表更符合 Clean Architecture 職責分離原則。
- 決策 2：Robin 明確要求「不能只有在 App 能操作」，且 Robin 平常主要透過 Telegram 跟 Robinson 互動，收到錯誤通知當下直接在 Telegram 回一行記錄解法，比切換到 App 更符合實際使用情境；沿用 FR-39b 應徵狀態已驗證過的單行指令模式，降低設計與實作風險。
- 決策 3：Robin 需要知道「這則私訊對應哪個 ID」才能下指令，只能在通知當下就把 ID 一併附上，不能事後才生成。

**替代方案**：
- 決策 1 替代方案（已否決，即本文件初版）：`complaints` 表直接加 `resolution` 欄位——不採用，因為 Robin 明確表示使用者客訴不需要這個欄位，混用會讓「客訴」跟「錯誤」兩種性質不同的資料共用一張表、一套編輯規則，語意不乾淨。

**後果**：
- robinson SPEC.md 新增 FR-19j（Placeholder），定義 `system_error_reports` 表、`_notify_robin_of_error()` 的擴充、Telegram 新指令設計。
- FR-19j 的後端部分（`system_error_reports` 表、`webhook.py`、Telegram 指令）已於 2026-08-10 獨立完成並上線（見 robinson SPEC.md FR-19j、PROGRESS.md 對應里程碑），不再是 Step 4.4／4.5 的待辦事項。**App 頁面歸屬子 Step（2026-08-10 定案）**：「客訴回饋頁」本質上是一個唯讀分析頁面（僅「解法」欄位破例可編輯，見上方本 ADR 決策 1），跟待辦/體態/記帳/心情/求職/考試/技術分享等其他唯讀分析頁面性質相同，一併排進 Step 4.4/4.5 的「唯讀分析」子 Step 開發，不需要另外拆一個獨立 Step；解法欄位的可編輯支援（呼叫既有 `system_errors.update_resolution()`）在做這個頁面時順便一起完成。
- `complaints` 表維持原樣不變，本文件先前提案的 migration 不再需要。

**狀態**：accepted
